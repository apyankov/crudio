# Система AI-агентов для развития эталонного CRUD-приложения
### Vision & System Design — v1

> Документ подготовлен для экспертного обзора.
> Статус: **черновик, открыт для обсуждения**.

---

## 1. Суть идеи

Создать систему, в которой AI-агенты **самостоятельно развивают эталонное CRUD-приложение**:
- исследуют, какой функционал актуален в индустрии
- формулируют задачу и согласуют с человеком
- реализуют код по всем слоям (backend + frontend)
- пишут тесты, проходят CI
- открывают PR на код-ревью
- деплоят на test-стенд
- записывают обучающий ролик
- обновляют документацию
- ведут полный audit trail решений, промптов, диффов и артефактов

Эталонное CRUD-приложение — это не просто демо. Это **живой артефакт**: непрерывно обновляющийся эталон лучших практик, который одновременно является рабочим кодом, обучающим материалом и витриной актуального стека.

### Роли агентов и разделение ответственности

Чтобы не создавать "одного суперагента, который делает всё", система строится на специализированных ролях:

| Роль | Что делает | AI-адаптер |
|------|-----------|------------|
| **Research Agent** | Исследует веб/документацию, оценивает библиотеки и паттерны, пишет proposal | Research model adapter |
| **Dev Agent** | Модифицирует код, пишет тесты, обновляет OpenAPI, правит UI-компоненты | Code model adapter |
| **Review Agent** | Проверяет coherence диффа, валидирует архитектурные границы, запускает policy checks | Review model adapter |
| **Content Agent** | Обновляет документацию, готовит скрипт туториала, генерирует release notes, пишет скринкаст | Code model adapter |
| **Policy Engine** | Обязательный слой: контролирует границы папок, определяет риск-уровни, блокирует небезопасные операции | — (детерминированная логика) |

Каждый AI-адаптер — это абстракция над конкретным провайдером. Смена провайдера или модели для одной роли не затрагивает остальные. Для задач с высокой нагрузкой (research) можно использовать более дешёвую модель, для генерации кода — более мощную.

### Coordination hub: выбор task-менеджера

> **Примечание.** В ходе обсуждения первым рассматривался Trello — исключительно потому, что он уже знаком. Это не финальный выбор.
>
> Предпочтительнее развернуть **self-hosted task-менеджер**, чтобы:
> - данные и задачи хранились на своей инфраструктуре
> - AI-агенты подключались к нему через **MCP** (Model Context Protocol) — стандартный способ давать LLM инструменты для работы с внешними системами
> - UI был привычен тем, кто работал с Trello / Jira (Kanban-доска, карточки, списки)
>
> **Рабочий вариант — Vikunja:**
> Vikunja — open-source self-hosted task manager (Go + Vue), разворачивается в Docker, имеет REST API, Kanban-вид, привычный UI. Серьёзных подводных камней нет; два небольших момента:
> - нет нативной n8n-ноды (используются HTTP Request ноды — это стандартная практика)
> - нет готового официального MCP-сервера, но REST API задокументирован хорошо, и MCP-обёртку над ним несложно написать самостоятельно или найти в community
>
> Итого: **Vikunja** берём как рабочий вариант, к нему возвращаемся при настройке инфраструктуры.

Coordination hub — **шина взаимодействия** между всеми участниками:

| Участники | Механизм |
|-----------|----------|
| Агент → Человек | Карточка в "❓ Awaiting Input", человек отвечает комментарием |
| Агент → Агент | Карточка в "📥 Inbox", другой агент подхватывает |
| Человек → Агент | Карточка в "📥 Inbox", агент берёт в работу |

Telegram — только **push-уведомления**: "PR открыт", "CI упал", "вопрос в task-менеджере".

#### Структура доски (Vikunja)

> Переходы между статусами являются триггерами для n8n workflows. Например: карточка переходит в "Approved" → n8n запускает ветку реализации. Список статусов намеренно предварительный и будет уточняться по мере реального использования.

| Список | Назначение |
|--------|------------|
| 📥 Inbox | Новые задачи |
| 🔬 In Research | Агент исследует |
| ❓ Awaiting Human Input | Вопрос агента → ждёт ответа |
| ✅ Approved | Человек одобрил |
| 🚧 In Progress | Агент реализует |
| 🔍 In Review | MR открыт, ревью человека |
| 🔴 CI Failed | CI упал — нужно исправить (агент или человек) |
| ✅ Done | Завершено |
| ❌ Blocked | Нужна ручная интервенция |

## 5. MVP: "field/type expansion" — добавление нового типа поля

### Task N0 — обязательное условие перед стартом агентов

⚠ Агентное расширение имеет смысл только при наличии рабочего базового CRUD.

До запуска агентного цикла должно существовать:
- одна рабочая сущность (entity)
- одно рабочее поле типа String
- полный CRUD end-to-end: API + UI
- тесты проходят
- GitLab CI активен и зелёный

Только после выполнения N0 агенты получают право запускать expansion-циклы.

---

### Почему этот сценарий первым

- Предсказуемые точки изменения в коде
- Полный цикл: research → implement → test → PR
- Наглядный результат для проверки системы

### Чеклист изменений при добавлении нового типа поля

> ⚠ MR автоматически блокируется, если агент не затронул все обязательные секции чеклиста.

**Backend (Java/Spring Data MongoDB):**

| Слой | Что меняет агент |
|------|-----------------|
| `@Document` класс | Добавляет поле с нужным типом |
| DTO | Добавляет поле + Bean Validation аннотации |
| OpenAPI YAML | Добавляет свойство в schema |
| Unit-тесты (JUnit) | Граничные значения, null-cases |
| Integration-тесты | Сохранение/чтение через репозиторий |

*Миграции не нужны — MongoDB schema-less.*

**Frontend (Vue3 + PrimeVue):**

> ⚠ Стратегический принцип: типы полей должны маппиться на существующие PrimeVue-компоненты. Создавать кастомные UI-элементы — только если подходящего компонента в PrimeVue нет.

| Тип поля | PrimeVue компонент | Особенности |
|----------|--------------------|-------------|
| `Money / Decimal` | `<InputNumber mode="currency">` | валюта, precision |
| `DateTime` | `<DatePicker>` | формат, timezone |
| `Enum` | `<Select>` | значения из API |
| `Boolean` | `<ToggleSwitch>` | — |
| `File` | `<FileUpload>` | multipart |
| `JSON / Object` | `<Textarea>` | валидация JSON |

Для каждого нового поля агент также обновляет:
- **форму создания/редактирования** (input + inline validation UI)
- **таблицу списка** (отображение значения в колонке)
- **фильтры/сортировку** (если тип данных это поддерживает)

**Документация:**

| Артефакт | Содержание |
|----------|------------|
| README / docs | Описание нового типа поля |
| Примеры payload | Пример запроса/ответа API с новым полем |
| Release notes | Запись об изменении в changelog |

### Пример первого рабочего цикла

```
Триггер (карточка в Vikunja, список Inbox):
  "Добавь поле createdAt типа DateTime к сущности Sample"

n8n workflow:
  1. Принять задачу из Vikunja (через MCP)
  2. AI читает: Sample.java, SampleDto.java, api.yaml, SampleForm.vue
  3. AI генерирует изменения по всем файлам
  4. Shell: git checkout -b agent/add-datetime-createdat
  5. Записать изменённые файлы
  6. Shell: git commit -m "feat: add createdAt DateTime field to Sample"
  7. GitLab API: открыть Merge Request с описанием
  8. Telegram: "MR открыт: https://gitlab.com/.../merge_requests/42"
  9. Task manager: переместить карточку в "🔍 In Review"
```

## 6. Принципы проектирования

- **Safety by construction** — агент никогда не пушит в `main`; только MR; только после approvals
- **Deterministic verification** — тесты + линтеры + GitLab CI — это "истина"
- **Small diffs** — один MR = одно поле / одно изменение
- **Reproducibility** — зафиксированный toolchain, dockerized builds
- **Separation of duties** — Research Agent ≠ Dev Agent ≠ Content Agent
- **Observability** — n8n хранит историю каждого запуска; Audit Trail логирует промпты и диффы
- **Provider agnosticism** — три независимых AI-адаптера (Research / Code / Review); смена провайдера или модели для одной роли не затрагивает остальные; возможно смешивание local + hosted моделей

## 7. Дорожная карта уровней зрелости

| Уровень | Название | Что умеет система |
|---------|----------|--------------------|
| **A** ← *старт* | Assisted template evolution | Добавляет поля/типы в строгом скоупе. Только MR, только CI, только разрешённые папки. |
| **B** | Autonomous backlog + gated execution | Ведёт бэклог улучшений. Сама предлагает задачи. Человек одобряет в task-менеджере. Авто-merge при CI pass. |
| **C** | Multi-target generator | Одна доменная модель → несколько стеков (+ PostgreSQL, + FastAPI, + NestJS). Агенты синхронизируют шаблоны. |
| **D** | Productized internal platform | Политики, compliance, security scanning, SBOM, org-wide стандарты, release notes. |

## 8. Audit Trail и observability

Система логирует всё:

| Что логируется | Зачем |
|----------------|-------|
| Промпты агентов | Воспроизводимость, дебаггинг |
| Источники research | Трассируемость решений |
| Сгенерированные планы | Governance review |
| Применённые диффы | История изменений |
| Вывод CI | Диагностика сбоев |
| Решения человека | Аудит approvals |
| Финальные артефакты | Документация, видео, release notes |

**Важно:** до включения production-level логирования необходимо определить политику обработки чувствительных данных — код может содержать секреты, токены, PII.

## 9. Level B preview — Self-improving agents

Вводится после стабилизации Level A. Концепции для проработки:

| Концепт | Суть |
|---------|------|
| **Prompt version registry** | Промпты агентов версионируются как код; изменения отслеживаются и откатываются |
| **Postmortem analysis** | После каждого CI failure агент анализирует причину и предлагает правку промпта/логики |
| **Метрики** | time-to-merge, CI failure rate, количество ревью-итераций — основа для оценки качества агентов |
| **Controlled prompt updates** | Обновление промптов проходит через Policy Engine; не любой агент может изменить собственный промпт |

## 10. Открытые вопросы (TBD)

| Вопрос | Статус |
|--------|--------|
| AI-провайдер | Не выбран. Абстрагирован по ролям. Выбрать перед первым запуском. |
| Test environment | Нужно создать. Отдельный сервер или тот же, что n8n. |
| Content Agent (видеозапись) | Не проработан. Отложен до уровня B. |
| Self-improvement агентов | Концептуально заложен. Реализация — уровень B+. |
| Task manager setup | Развернуть Vikunja в Docker, создать доску, написать/найти MCP-сервер для интеграции с n8n. |
| GitLab: группа/репо | Нужно уточнить структуру: монорепо или отдельные репо для backend/frontend? |
| Risk scoring model | Что считать "рискованным" изменением? Какой порог требует эскалации? |
| Sandbox isolation | Как изолировать выполнение агента? Docker-in-Docker, отдельный runner? |
| Prompt versioning | Как версионировать промпты агентов? Git? Отдельное хранилище? |
| Memory / RAG | Как агент хранит знания о кодовой базе? RAG поверх репозитория? |
| Sensitive data policy | Что логировать, что маскировать? Нужна политика до production-логирования. |
| OpenAPI: contract-first или generate | Контракт пишется руками или генерируется из кода? |

## 11. Ближайшие шаги (Level A, первый рабочий цикл)

1. **[Task N0] Собрать базовый CRUD вручную** — одна сущность, поле String, полный цикл API + UI, CI зелёный
2. **Развернуть n8n** на Ubuntu-сервере в Docker
3. **Развернуть Vikunja** в Docker и создать доску с описанными списками
4. **Подключить Telegram-бот** (push notifications)
5. **Выбрать AI-провайдера** и настроить адаптеры по ролям (Research / Code / Review)
6. **Описать структуру эталонного приложения** — folder boundaries, какие файлы агент читает и пишет
7. **Создать первый n8n workflow** — Vikunja trigger (MCP) → AI → GitLab MR → Telegram notify
8. **Прогнать первый цикл** на примере "добавить поле DateTime"
9. **Итерировать** — улучшать промпты, добавлять обработку ошибок, расширять скоуп
