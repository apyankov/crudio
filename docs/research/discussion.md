## Итерация 1 — Постановка задачи

**Дата:** 2026-02-27

### Идея (Феликс)

Система, где AI-агенты самостоятятельно:
1. Исследуют интернет на предмет актуальных практик
2. Находят, что можно добавить в эталонное CRUD-приложение
3. Формулируют задачу
4. Согласуют с человеком через Telegram
5. Реализуют код
6. Пишут тесты
7. Деплоят на test-стенд
8. Записывают обучающий ролик
9. Дополняют документацию

### Понимание (Claude)

CRUD-приложение — **живой артефакт**: постоянно обновляющийся эталон лучших практик, который одновременно является рабочим кодом, обучающим материалом и витриной актуальности.

### Масштаб системы (от узкого к широкому)

| Уровень | Описание |
|---------|----------|
| **Минимум** | Агент добавляет один тип данных в CRUD, пишет тест, обновляет README |
| **Базовый** | Полный цикл: research → plan → code → test → deploy → document |
| **Расширенный** | Мультиагентная оркестрация, Human-in-the-Loop через Telegram |
| **Продвинутый** | Видеоконтент, самообучение агентов, несколько стеков |
| **Платформенный** | Тиражируемый фреймворк для любых "живых эталонов" |

```
│  Agent   │   │    Agent     │  │  (Telegram)  │
└──────────┘   └──────────────┘  └──────────────┘

┌──────────┐   ┌──────────────┐  ┌──────────────┐
```

| Memory/Knowledge Base | Явно как отдельный компонент | Включён в Audit Trail | Объединяем: Audit Trail + Memory |
| Multi-target (Level C) | Упомянут как "фреймворк" | Явно: Java → Python/FastAPI → Node/NestJS → UI | Важная точка роста, фиксируем |

### Ключевые добавления в план после анализа ChatGPT

1. **Уровни A/B/C/D** — заменяют размытые "направления". Даём системе чёткую дорожную карту роста.

2. **Signal Intake** — первый шаг конвейера теперь явный: сигналы приходят из нескольких источников (не только "агент смотрит интернет").

3. **Policy Engine** — отдельный компонент. Агент не просто решает что делать, а проходит через политику: какой риск, что разрешено, нужна ли эскалация.

4. **Audit Trail** — всё логируется. Решения, промпты, диффы. Это и governance, и основа для self-improvement.

5. **Design principles** явно сформулированы — теперь это часть плана, а не подразумевается.

6. **Конкретный MVP** — добавление нового типа поля с 7 предсказуемыми точками изменения. Идеально для первого рабочего цикла.

### Что ChatGPT пропустил (остаётся уникальным в нашем плане)

- **Self-improving system** — агенты улучшают собственные промпты и паттерны на основе прошлых итераций
- **Narrator/Content Agent** как полноправный агент-участник конвейера
- **Фреймворк тиражирования** — не просто "несколько стеков", а воспроизводимая система для любого "живого эталона"

- Архитектура: ✅ сформирована (конвейер + компоненты)
- Уровни зрелости: ✅ A/B/C/D
- MVP: ✅ field/type expansion
- Принципы: ✅ зафиксированы

## Итерация 3 — Стек подтверждён

**Дата:** 2026-02-27

### Ответ Феликса

> **Backend:** Java / Spring
> **Frontend:** Vue 3, Vite, Tailwind CSS, PrimeVue

### Что это значит для MVP "field/type expansion"

Теперь конкретно знаем, что агент должен менять при добавлении нового типа поля:

**Backend (Java/Spring) — точки изменения:**

| Слой | Файл / артефакт | Пример для типа `Money` |
|------|----------------|-------------------------|
| Entity | `@Entity` класс | `private BigDecimal price;` |
| Validation | DTO + Bean Validation | `@DecimalMin("0.0")` |
| Persistence | JPA / mapping | тип колонки, precision/scale |
| API schema | `OpenAPI yaml` | `type: number, format: decimal` |
| Tests | JUnit + Spring Boot Test | граничные значения |

**Frontend (Vue3 + PrimeVue) — точки изменения:**

| Тип поля | PrimeVue компонент | Tailwind / особенности |
|----------|--------------------|------------------------|
| `Money / Decimal` | `<InputNumber mode="currency">` | суффикс/префикс валюты |
| `Date / DateTime` | `<DatePicker>` | формат, timezone |
| `Enum` | `<Select>` / `<Dropdown>` | список значений из API |
| `JSON / Object` | `<Textarea>` или кастомный | валидация JSON |
| `File / Blob` | `<FileUpload>` | multipart, preview |
| `Geo / Coordinates` | `<InputGroup>` (lat + lng) | два поля, карта опционально |

PrimeVue здесь — ключевой актив: для большинства типов уже есть готовый компонент, агенту нужно лишь правильно его сконфигурировать.

- PostgreSQL / MySQL → JPA + Hibernate, `@Column(precision=...)`, liquibase/flyway миграции
- MongoDB → Spring Data MongoDB, `@Document`, нет строгой схемы

## Итерация 4 — Уровень A. AI-провайдер TBD.

**Дата:** 2026-02-27

### Ответ Феликса

> **Уровень старта:** A — "Assisted template evolution"
> **AI-провайдер:** не определён

### Что значит Level A на практике

Жёсткие ограничения — это не слабость, это правильно для старта:

- Агент работает **только в определённых папках** (entity, dto, repository, service, controller, openapi, vue-компоненты, тесты)
- Агент **только добавляет/изменяет** — не удаляет, не рефакторит чужой код
- Каждое изменение **проходит CI** (сборка + тесты) — иначе не мержится
- Агент **не пушит в main** — только открывает PR
- Скоуп одного PR = одно поле / один тип данных

Конкретный flow Level A для MVP:

```
Вход: "Добавь поле price типа Money к сущности Product"
  ↓
Агент читает существующий код (entity, DTO, OpenAPI, Vue-форма)
  ↓
Агент генерирует diff по всем слоям
  ↓
Открывает PR с описанием изменений
  ↓
CI: сборка + тесты
  ↓
Человек ревьюит → merge
```

### AI-провайдер: сравнение вариантов для этой задачи

Основные требования от провайдера в контексте Level A:
- Генерация кода на Java и Vue/TypeScript
- Понимание существующих паттернов (читает код → воспроизводит стиль)
- Tool use: файловые операции, git, запуск команд
- Контекстное окно: нужно читать несколько файлов одновременно

| Провайдер | Сильные стороны | Слабые стороны | Tool use |
|-----------|-----------------|----------------|----------|
| **Claude (Anthropic)** | Сильный reasoning, отличная работа с кодом, большой контекст (200k), следует инструкциям точно | Платный | ✅ Очень хороший |
| **GPT-4o (OpenAI)** | Хорошая генерация кода, большая экосистема, Assistants API | Бывает "многословен", дороже на объёмах | ✅ Хороший |
| **Gemini 2.0 Flash** | Дешевле, быстрее, большой контекст (1M) | Менее предсказуем в agentic сценариях | ✅ Хороший |
| **Локальные (Ollama + Qwen/Llama)** | Бесплатно, данные не уходят наружу | Слабее на сложных reasoning-задачах, нужна GPU | ⚠️ Ограниченный |
| **Гибрид** | Дешёвая модель для research, сильная для code | Сложнее поддерживать | ✅ Гибко |

**Для Level A рекомендация:** можно стартовать с одним провайдером и абстрагировать вызов через общий интерфейс — тогда смена провайдера будет дешёвой операцией.

### Что разблокируется сейчас (без финального выбора провайдера)

Следующие шаги не зависят от выбора провайдера:
1. Описать структуру эталонного приложения (какие папки, какие паттерны)
2. Определить policy: что агенту разрешено трогать
3. Спроектировать формат "задания" агенту (input spec)
4. Выбрать orchestrator

## Итерация 5 — MongoDB, PR-only approval, n8n

**Дата:** 2026-02-27

### Ответ Феликса

> **Persistence:** MongoDB (позже возможно PostgreSQL / Supabase)
> **Approval:** агент только открывает PR; позже авто-merge при прохождении CI
> **Orchestrator:** n8n (однозначно)

---

### Импликации каждого решения

#### MongoDB → Spring Data MongoDB

Меняет persistence-слой по сравнению с JPA:

| Аспект | JPA/Hibernate | Spring Data MongoDB |
|--------|---------------|---------------------|
| Аннотация | `@Entity` | `@Document` |
| Миграции | Liquibase / Flyway | Нет (schema-less) |
| Типы | `@Column(precision=10)` | нативные BSON-типы |
| Money/Decimal | `BigDecimal` + column def | `Decimal128` или `BigDecimal` |
| DateTime | `LocalDateTime` + JPA | `Date` / `LocalDateTime` (авто) |
| Enum | `@Enumerated` | строка или int нативно |

**Вывод для агента:** нет нужды генерировать миграции — только изменения в `@Document`-классе и DTO. Это упрощает Level A.

Но: при добавлении PostgreSQL позже агент должен будет уметь генерировать оба варианта (стратегия "dual persistence" или профили Spring).

#### PR-only approval — самый безопасный старт

Агент имеет права:
- ✅ читать кодовую базу
- ✅ создавать ветку
- ✅ писать файлы в ветке
- ✅ открывать PR с описанием
- ❌ мержить
- ❌ пушить в main
- ❌ удалять ветки / файлы (кроме своих)

PR = точка человеческого контроля. Агент обязан описать в PR: что сделал, почему, какие тесты добавил, что проверить.

#### n8n как оркестратор — конкретные возможности

n8n покрывает весь Level A нативно:

```
[Trigger] ──────────────────────────────────────────────────────┐
  Telegram message / schedule / webhook                          │
                                                                 ↓
[Research] ─── HTTP node → AI provider (любой через API)
                                                                 ↓
[Proposal] ─── Telegram node → отправить предложение человеку
                                                                 ↓
[Wait] ──────── Telegram callback (approve / reject / edit)
                                                                 ↓
[Generate] ──── HTTP node → AI: сгенерировать изменения кода
                                                                 ↓
[Git ops] ───── Shell node или GitHub/GitLab node:
                  create branch → write files → commit → open PR
                                                                 ↓
[Notify] ─────── Telegram node → "PR открыт: [ссылка]"
                                                                 ↓
[CI webhook] ─── GitHub/GitLab webhook → n8n:
                  CI pass → notify Telegram
                  CI fail → notify + attach logs
```

n8n здесь — это и визуальный дебаггер workflow, и история запусков, и retry-логика, и переключение провайдера за 1 шаг (поменять HTTP node).

```
  6. Shell: git commit + git push + gh pr create
  7. Telegram: "PR открыт: https://github.com/.../pull/42"
```

## Итерация 6 — Инфраструктура закрыта. Trello как coordination hub.

**Дата:** 2026-02-27

### Ответ Феликса

> **Git:** GitLab
> **CI:** GitLab CI
> **Telegram:** только оповещения (простейший бот)
> **Coordination:** Trello — вопросы агента к человеку, задачи агент→агент, задачи человек→агент
> **n8n:** Docker на отдельном Ubuntu-сервере
> **Test environment:** отдельный сервер (возможно, совмещён с n8n-сервером)

### Ключевое архитектурное решение: Trello как центральный hub

Это значимый сдвиг: Trello — не просто таск-трекер, это **шина координации** между всеми участниками системы.

Три типа взаимодействий через Trello:
1. **Агент → Человек:** вопрос (карточка в списке "Awaiting Input") → человек отвечает в комментарии
2. **Агент → Агент:** задача (карточка) → другой агент её подхватывает
3. **Человек → Агент:** задача (карточка) → агент берёт в работу

n8n имеет нативные Trello-ноды — интеграция без кастомного кода.

Telegram остаётся каналом **push-уведомлений**: "PR открыт", "CI упал", "Вопрос в Trello".

### Итоговая инфраструктурная карта

```
┌─────────────────────────────────────────────────────┐
│                  Ubuntu Server A                     │
│   n8n (Docker) + AI Agent Runtime                   │
│   (возможно: test environment тоже здесь)           │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP / webhook
         ┌─────────────┼─────────────┐
         ↓             ↓             ↓
    [GitLab]      [Trello]      [AI Provider]
    Git + CI      Task hub      LLM API
         │             │
         └──────────────────→ [Telegram Bot]
                              push notifications
```

### Предлагаемая структура Trello-доски

| Список | Назначение |
|--------|------------|
| 📥 Inbox | Новые задачи (от человека или агента-researcher) |
| 🔬 In Research | Агент исследует |
| ❓ Awaiting Human Input | Агент задал вопрос — ждёт ответа человека |
| ✅ Approved | Человек одобрил — агент может реализовывать |
| 🚧 In Progress | Агент генерирует код |
| 🔍 In Review | PR открыт — человек ревьюит |
| ✅ Done | Завершено |
| ❌ Blocked / Failed | Проблема, нужна ручная интервенция |

Лейблы карточек: `feature`, `question`, `agent-task`, `human-task`, `bug`
